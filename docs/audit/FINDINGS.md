## P0 — hitna zaštita / incident review

### SEC-01 — Review API response exposure (baseline P0; source-branch hotfix)

**Baseline evidence:** prije ove izmjene `GET /api/reviews/:id` je bio `@Public()` i `ReviewsService.findOne` uključivao je `stylist.user: true`; review list je dopuštao da `approved=false`/izostanak filtera vrati pending zapise. `User` model i dalje sadrži osjetljive account scalars ([`User` model](../../backend/prisma/schema.prisma#L44-L64)); početno stanje je zabilježeno u prethodnom audit pregledu.

**Hotfix u ovom branch-u:** [`REVIEW_DISPLAY_SELECT`](../../backend/src/reviews/reviews.service.ts#L16-L30) bira samo review display polja i ime/prezime; nema `User` account polja, `userId` ni reservation ID. Public list [`findAllPublic`](../../backend/src/reviews/reviews.service.ts#L102-L155) uvijek postavlja `isApproved: true`. Detail handler [`findOne`](../../backend/src/reviews/reviews.controller.ts#L60-L63) više nije `@Public()` i zato je zaštićen globalnim JWT guardom; service [`findOne`](../../backend/src/reviews/reviews.service.ts#L178-L185) dodatno ograničava lookup na `isApproved: true`, pa pending/nepostojeći ID oba vraćaju NotFound. Public featured/random također koristi isti select ([`findOneRandomApproved`](../../backend/src/reviews/reviews.service.ts#L87-L100)). Review moderation list je izdvojena na [`GET /api/reviews/admin`](../../backend/src/reviews/reviews.controller.ts#L45-L58), zaštićena sa `RolesGuard` i `SYSTEM_ADMIN`/`OWNER`. Controller regression test potvrđuje da approved list ostaje public, ali detail nema public metadata; service tests pokrivaju query/projection.

**Uticaj baseline-a:** prije hotfix-a, anonimni ID lookup je mogao vratiti sve `User` scalar fields za povezanog stilistu, a javni list pending review-e. U source branch-u detail sada zahtijeva JWT, a javni list samo approved zapise i display polja. Ovo je bila potencijalna exposure putanja; nije urađen HTTP request niti potvrđen deployment/access log, pa se ne tvrdi eksfiltracija.

**Preostala reakcija:** provjeriti access logove, deployed app version i exposure window; prema incident policy-ju procijeniti poništenje verification tokena / credential reset. Source branch promjena sama po sebi ne utiče na već deployanu aplikaciju.

**Stanje:** source-branch containment uključuje uklanjanje `@Public()` sa detail rute, approved-only display queries i admin-only moderation route; review service/controller unit tests prolaze, a `security-contract.spec.ts` koristi stvarni Nest routing, JWT guard i service stub da provjeri anonymous 401, authenticated display response i pending 404. Novi `backend/test/security-reviews-blog.e2e-spec.ts` dodaje stvarni Nest HTTP/JWT/role path i Prisma queries uz synthetic PostgreSQL fixtures; local DB nije dostupan u sandboxu, a disposable PostgreSQL CI run `39683834085` je prošao. Backend build/typecheck with generated Prisma passes in CI run `39683834085`; deployed HTTP provjera i incident review ostaju otvoreni.

### OPS-SEC-01 — Vjerodajnice su ranije bile commitovane; historija ostaje

**Dokaz/stanje:** tokom početne audit faze uklonjeni su iz indexa `backend/.env`, `frontend/.env`, `mobile/.env` i Firebase Admin JSON. Na nastavku rada hygiene provjera neočekivano je utvrdila da su sva četiri path-a opet bila u Git indexu (tri lokalna `.env` fajla postoje; service-account JSON nije bio u workspaceu). U ovom nastavku `git rm --cached -f` ponovo je uklonio index zapise bez brisanja lokalnih env fajlova; `git ls-files` ih više ne navodi, a `git check-ignore` potvrđuje ignore pravila. Git historija nije prepisana (namjerno), tako da su stari blobovi i dalje dostupni kroz commit historiju ako su već pushani/klonirani.

**Uticaj:** uklanjanje iz posljednjeg tree-a ne opoziva DB, SMTP, JWT, encryption ili Firebase vjerodajnice. Nisu ispisane vrijednosti i nisu testirane; ne zaključujemo koji su još aktivni.

**Preporučena reakcija:** credential owner neka pregleda istoriju i deployment secret manager izvan ovog repozitorija; rotira/revokuje svaki nekad commitovan secret; invalidira izdate tokene gdje je potrebno; provjeri Firebase audit i DB/SMTP logove. **Ne rotirati `APP_SETTINGS_ENCRYPTION_KEY` bez kontrolisanog re-encryption/dual-key plana**, jer baza može imati enkriptovane AppSetting vrijednosti.

**Repo-side provjera (2026-10-22; samo putanje/commit metapodaci):** Trenutni tracked tree nema poznate privatne credential putanje; `git ls-files` za env/credential nazivni filter vraća samo `.env.example`, `check_repo_hygiene.py` prolazi za 1.097 tracked putanja (samo imena), a `git check-ignore` potvrđuje ignore pravila za tri lokalne `.env` putanje. Nije provjeravano postoje li te lokalne datoteke i njihov sadržaj nije otvaran. Lokalni checkout je shallow, pa njegov `git log` ne obuhvata stariju historiju. GitHub tree/path API provjera koristila je samo putanje, commit hash/datume i tree metapodatke (bez blobova, patch-eva ili secret vrijednosti): parent stabla `b71e686` (`5b6921a`) sadrži tri `.env` putanje i jedan Firebase Admin SDK service-account JSON; tree nakon `b71e686` (2026-10-21) ih više ne sadrži. Path-only historija evidentira backend `.env` u `c13090e`, `f908d94`, `168a33e`; frontend `.env` u `76a0283`, `0e85e36`; mobile `.env` u `884163c`, `db80a2a`; service-account JSON u `b8975dd`; uklanjanje je vidljivo u `b71e686`. Ovo potvrđuje samo ranije putanje i uklanjanje iz tree-a, ne koje su vrijednosti bile u fajlovima, jesu li još aktivne, jesu li kopirane u artefakte/cache/clone-ove ili je li izvršena rotacija.

**Preostali owner zadatak:** credential owner treba van ovog repozitorija pregledati potpuni Git history i build/artifact/cache kopije, secret manager i deployed app verzije; klasifikovati svaki stvarni secret iz historijskih fajlova, rotirati/revokovati aktivne vrijednosti i pregledati Firebase/DB/SMTP/auth logove. `APP_SETTINGS_ENCRYPTION_KEY` ne rotirati bez kontrolisanog re-encryption/dual-key plana. Agent nije čitao ni ispisivao vrijednosti, nije mijenjao env/secret fajlove i nije pristupio produkciji, bazi, Redis-u ili deploymentu.

## P1 — visoko

### SEC-02 — `/api/users/clients` baseline returned full User records to stylists (source-branch mitigation)

**Baseline:** previous controller allowed `SYSTEM_ADMIN`, `OWNER`, and `STYLIST`; previous service used a scalar `include` (plus `userRoles`/`stylistProfile`) and returned all matching users if pagination was absent. The [`User` model](../../backend/prisma/schema.prisma#L44-L64) contains password hashes, email-verification tokens, social IDs and contact PII.

**Mitigation on this branch:** `GET /api/users/clients` remains available to those staff roles only as a bounded picker. [`CLIENT_PICKER_SELECT`](../../backend/src/users/users.service.ts#L16-L22) returns only `id`, `username`, first/last name and `gender`; total client count and account scalars are not returned. Picker search matches username/name only; email search is reserved for admin. `ClientListQueryDto` validates page/pageSize/search length ([DTO](../../backend/src/users/dto/client-list-query.dto.ts#L11-L30)); service defaults/caps page size and clamps page to result bounds ([picker service](../../backend/src/users/users.service.ts#L134-L154)). The admin user-management screen now uses separate [`GET /api/users/clients/admin`](../../backend/src/users/users.controller.ts#L44-L52), role-guarded for `SYSTEM_ADMIN`/`OWNER`, with an explicit UI-only allowlist ([`ADMIN_CLIENT_SELECT`](../../backend/src/users/users.service.ts#L24-L37)); sensitive password/token/social fields are not selected. `GET /api/users/:id` remains self/admin/owner-only and now uses [`USER_DETAIL_SELECT`](../../backend/src/users/users.service.ts#L41-L63), which omits authentication hashes/tokens and social IDs even for self/admin reads. Booking-picker consumers continue using the minimal route.

**Impact baseline:** before the branch change, a stylist token could potentially receive hashes/tokens/contact data and an unbounded result. HTTP role/response testing had not been executed; production exposure is not established.

**State:** query/select/pagination and route-role unit tests are included and pass; frontend build passes. `GET /api/users/:id` now returns a safe detail projection while retaining self/admin/owner access rules. Disposable PostgreSQL HTTP tests now cover client self-vs-other detail, stylist access boundaries, owner/admin reads, picker/admin projections, secret-field omission, staff-vs-admin email search, and pagination; these SEC-02 assertions passed disposable PostgreSQL CI run `39736393872`. Local PostgreSQL is unavailable. Source-branch mitigation only—production/live HTTP and deployment verification remain pending.

### SEC-04 — Javno posluživanje upload-a i nepotpuna delete/reference zaštita

**Baseline (source inventory prije privacy promjena u ovoj grani):**

- `main.ts` je statički servirao cijeli `UPLOAD_ROOT` pod `/uploads/` bez auth.
- `POST /api/uploads` je zahtijevao JWT, ali `entity` je samo birao poddirektorij bez privacy-class allowliste; service je vjerovao multipart `mimetype`, čuvao originalni SVG/PDF/Office fajl u istom root-u i nije radio signature sniff.
- `Upload` nije imao storage/consent klasu. Uploadi su vezani za `DailyLogImage`, `GalleryImage`, finance attachment/invoice zapise i direktne path reference (avatar, salon/service/blog/app logo, APK). Direktni static URL je zaobilazio API role filtre. Public Gallery category detail je vraćao puni `Upload` zapis prije eksplicitne projekcije.

**Ranija narrow delete mitigacija (2026-10-22):** `DELETE by-path-original` prima authenticated actor, ograničava brisanje na uploader ili `OWNER`/`SYSTEM_ADMIN`, provjerava poznate relacijske/putanjske reference i containment ispod root-a. Unit testovi prolaze 3 suite/13 testova; commit `2558d18` prošao CI run `39753417714`. Reference preflight nije atomski protiv konkurentnog write-a i ne rješava čitanje.

**Current source implementation progress (2026-10-23; nije deployano):** `main.ts` sada statički servira samo `UPLOAD_ROOT/public/` pod istim `/uploads/` prefixom; generic uploads po defaultu završavaju privatno pod `private/` uz `0700` direktorije i `0600` fajlove. Avatar je privatna, owner-bound varijanta po defaultu; samo sam korisnik može postaviti svoj avatar ili uključiti `isAvatarPublic`, a javni `/api/users/:id/avatar` route na svakom zahtjevu provjerava opt-in, vlasništvo i validnu privatnu image varijantu. Ova postavka važi samo za avatar/profile prikaz, ne za Gallery, oglase ili društvene mreže. Poseban owner/admin endpoint prima samo allowlisted brand/service/blog image assets i sanitizira ih u WEBP prije javnog upisa. Private files idu kroz JWT-protected content route sa per-resource/uploader/role provjerama, `no-store`, `nosniff` i attachment disposition za ne-sigurne inline MIME tipove. MIME se provjerava prema sadržaju, a ne samo client headeru; originalni SVG se ne služi javno. Public Gallery response koristi eksplicitnu projekciju. Ručne Gallery kategorije mogu dobiti neklijentske salon/proizvod materijale kroz category-bound upload koji ponovo kodira sliku u WEBP i postavlja `PUBLIC` tek nakon serverski obavezne `nonClientAssetConfirmed=true` potvrde; to je eksplicitna owner/admin attestation, ne automatsko prepoznavanje osoba, pa UI i API zabranjuju korištenje ovog toka za klijentske fotografije, koje se dodaju samo kroz birač aktivne saglasnosti. Obični `PUBLIC` upload iz generičkog/public-asset endpointa ne može se dodati u Gallery. Web `/galerija` prikazuje before/after feed koji filtrira aktivnu saglasnost. Draft APK se staginguje privatno; publish provjerava ZIP signature, SHA-256 i veličinu prije public kopije i DB release-update transakcije, uz eksplicitne private/public file mode-e.

**Migracija (source-only, neizvršena):** planner/runner klasificira legacy putanje konzervativno, tretira nepoznato/unlinked kao privatno, i ne smatra `Upload.storageClass=PUBLIC` samostalnom allowlistom. Javnost ostaje kroz eksplicitne direktne reference na odobrena brand/service/blog/settings/APK polja i kroz upload koji je kreiran namjenskim Gallery non-client tokom, povezan sa kategorijom, klase `PUBLIC` i putanje `gallery/`; sam `Upload.storageClass=PUBLIC` nije allowlista. Legacy Gallery-only/unlinked upload ostaje privatan dok ne postoji zaseban važeći consent derivative. Runner prepoznaje novije kategorijski povezane non-client assete za očuvanje buduće javnosti, dok stare/uncategorized gallery fajlove nastavlja mapirati privatno. Planner odbija javno/privatno path konflikte i invalid references, sanitizira samo allowlisted JPEG/PNG/WebP kopije i provjerava APK signature/hash/size. Review je otkrio mogući cutover leak: legacy `entity=public` i orphan fajlovi mogu fizički biti u budućem `UPLOAD_ROOT/public/`, gdje bi ostali statički dostupni iako DB putanje postanu privatne. Runner sada u dry-run-u broji takve unmapped fajlove; apply ih nakon copy/verify checksum-om premješta iz javnog static root-a u `private/legacy/public-root/<relative-path>` prije DB mappinga. Source bytes ostaju sačuvani privatno; DB rollback pokušava vratiti stare putanje. Planner test potvrđuje da se legacy source path `public/client-photo.jpg` mapira privatno; filesystem testovi pokrivaju quarantine/restore, provjeru checksum-a, static-root symlink i symlinked-cleanup-parent fail-closed ponašanje. Filesystem helper dodatno odbija traversal/symlink, radi preflight/mode enforcement, exclusive hard-link copy, checksum verification i cleanup pri djelimičnom neuspjehu. Synthetic migration planner + temporary-filesystem tests pass 2 suites/27 tests; the combined SEC-04/PRIV-01 mocked Jest run passes 10 suites/131 tests (2026-10-23) across Gallery, public daily-log, consent, users/avatar, uploads, reviews/stylists, migration and AppRelease, using a temporary Prisma enum/class stub and mocked service/repository boundaries. Runbook je [SEC-04-MIGRATION-RUNBOOK.md](SEC-04-MIGRATION-RUNBOOK.md); retention, restore-tested backup/rollback, data classification and owner cutover signoff remain open.

**Preostali uticaj/gates:** source promjena nije deployana, pa live served behavior nije potvrđen. Nisu testirani stvarni mount/permissions/hard-link support, Prisma generated types against the final schema, DB transaction/cutover, generic private-upload HTTP route in disposable PostgreSQL, browser/CORS ni deployment; current repository/service unit tests assert active current-policy consent, linked completed service, before/after eligibility and denial of OWNER/SYSTEM_ADMIN/uploader bypass for revoked consent derivatives. Retention, backup/rollback rehearsal, capacity, exact inventory and production cutover approval remain open; no automatic deletion exists. Do not restore the old app that exposes the entire root.

### PRIV-01 — Before/after galerija javno vraća fotografije bez consent polja u pregledanom modelu

At most one category may auto-publish pairs, enforced by a PostgreSQL partial unique index; the public pair mapper requires two distinct active-consented images and emits only consent-file paths/pair IDs, not service/date/client metadata. The migration planner preserves only new `PUBLIC` gallery assets still linked to a Gallery row under `gallery/`; legacy/unlinked items remain private unless separately consented. Web `/galerija` uses the consent-filtered before/after feed and manual categories; revoke removes consented items and blocks future derivative access. Gallery API does not return the full Upload model. ### BIZ-05 — Loyalty redeem/reversal concurrency i idempotency su slabi

**Baseline:** manual redemption/adjustment su ranije mijenjali saldo i ledger bez jedinstvenog request idempotency ključa; daily-log redemption je imao odvojene balance/marker writeove, a reversal je agregirao promjene bez per-original-ledger idempotency. **Source implementation and disposable-CI acceptance (2026-10-24; run `40140672041`):** `LoyaltyService` sada koristi transaction-aware point-mutation helper s account row lock-om, integer/Int-range provjerama, conditional balance update, ledger insert i tier recalc unutar iste transakcije. Za daily-log se koristi pohranjeni `DailyLogEntryServiceItem.unitPrice` kada postoji, inače service catalog cijena. ### OPS-01 — Scheduled jobs su process-local; duple instance mogu duplirati side-effects

`@nestjs/schedule` registruje četiri aktivna entrypointa u svakom backend procesu: minute [`ReservationDelayCron.tick`](../../backend/src/reservations/reservation-delay.cron.ts#L29), minute [`DailyLogCompletionOutboxService.retryPending`](../../backend/src/daily-log/daily-log-completion-outbox.service.ts#L166), dnevni KIF catch-up i mjesečni KUF rollover [`IncomeCronService`](../../backend/src/finance/income-cron.service.ts#L21). ### DEV-01 — Vite source config and tracked emitted config could diverge for local proxy routes (fixed in this branch)

`SocketContext` defaults to same-origin when `VITE_API_URL` is empty and Socket.IO uses its default `/socket.io` path. The tracked `vite.config.js` and `vite.config.ts` had diverged; installed Vite resolves `vite.config.js` before `.ts`, while the `dev` script invoked bare `vite`. The committed JS had `/socket.io` but no `/uploads`; the TS source had neither. This made local behavior dependent on stale generated config and did not proxy local upload URLs introduced in the env template. This was a development-config discrepancy, not evidence of a production API outage.

**Fix applied:** `vite.config.ts` now declares `/api`, `/auth`, `/socket.io` (WebSocket upgrade) and `/uploads` proxies; frontend `dev`, `build` and `preview` scripts explicitly select `vite.config.ts`. A tracked emitted JS config remains generated by `tsc -b` as the repo currently tracks it. `npm run build` passes after the change; browser/Socket.IO live connectivity was not exercised.

### DEV-02 — Frontend Docker build context omitted the shared business-date module (fixed; synthetic image CI passed)
